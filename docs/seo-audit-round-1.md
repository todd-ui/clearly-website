## 0. Method and environment limitations (read first)

This audit was performed against the committed source at the baseline commit and the site's build tooling. Two limitations shape what could be verified here, and both push certain verifications onto the **Netlify Deploy Preview** (which the reviewer inspects with a real browser and live URLs):

1. **Live production could not be fetched from the build sandbox.** Outbound requests to `getclearly.app` are blocked here (`curl` → `000`, WebFetch → `403`). So live HTTP status codes, live redirect behavior, and rendered-in-browser checks are **derived from committed files + `netlify.toml`** and must be confirmed on the Deploy Preview. They are not guesses, but they are not live-observed either.
2. **The production build cannot run end-to-end in the sandbox.** `npm run build` runs `build-blog.js`, which fetches all blog content from the **Notion API**. Notion is not on the sandbox network allowlist (`Host not in allowlist: api.notion.com`), so the blog/sitemap/feed regeneration step fails locally. It succeeds on Netlify (which has `NOTION_API_KEY` and network egress). See §7.

Everything that does **not** depend on those two things (JSON-LD validity, canonical/meta inventory, `robots.txt`, `llms.txt`↔sitemap consistency, redirect rules, the new validation tests) was verified directly in this environment.

### Site architecture (important context)

- **Static, hand-authored HTML.** All 12 landing pages + `faq/help/privacy/terms/professionals` are static HTML with all content, metadata, and JSON-LD in the initial HTML. **There is no client-side rendering of content** — so the common "metadata only appears after JS" SEO failure mode does not exist here. Nothing to fix on that front.
- **No private/authenticated routes exist in this repo.** The Clearly product is a separate iOS app; this repository is the marketing site only. The brief's "public vs private routes" / "auth entry point" checks are therefore **N/A** — there is no app login surface to protect or de-index.
- **Two build scripts:**
  - `build-blog.js` (runs on Netlify) — pulls posts from Notion and **generates** `blog/*.html` (101 posts), `blog.html`, `sitemap.xml`, and `feed.xml`. These four are **build artifacts**, not source of truth.
  - `build-site.js` (**manual, not in the Netlify build command**) — only injects the shared `_partials/header.html` / `footer.html` into landing pages. It does not touch metadata or JSON-LD.

## 1. Current-state inventory

### Page titles
Present and unique on every public route (see §2 table). No missing or duplicate `<title>`.
**Note (deferred, visible):** homepage `<title>` = *"Clearly — Co-Parenting Resolved"* but `og:title`/`twitter:title` = *"Clearly — Change the Conversation"*. Choosing one tagline is a copy decision → deferred.

### Meta descriptions
Present on all landing pages and 101/101 blog posts. Lengths reasonable. No action this round.

### Canonical tags
Present, absolute, and self-referential on every content page (verified by the new `seo-check.js`, which fails the build if any canonical is missing/relative/duplicated). 404 page correctly has none.

### Robots directives (meta)
All content pages emit `index, follow` (the comparison page adds `max-snippet:-1, max-image-preview:large, max-video-preview:-1`). **No accidental `noindex` anywhere** — verified by grep across all HTML. Nothing is unintentionally blocked at the meta level.

### robots.txt
Strong. Allows all, disallows only `/_partials/`, `/node_modules/`, `/.netlify/`. Includes an explicit, comprehensive **AI-crawler allowlist** (GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot, Google-Extended, Applebot/Applebot-Extended, CCBot, Amazonbot, Meta-ExternalAgent, Bytespider, YouBot, Diffbot, MistralAI-User, cohere, etc.). No AI crawler is blocked. No change needed.

### XML sitemap
Generated by `build-blog.js`. **Issues found and fixed this round** (see §3): it listed `/alignment/` (a 301 redirect source) and **omitted the 6 state child-support calculator pages** that exist and are internally linked.
**Deferred:** every `<lastmod>` is stamped with the build date (`${today}`), so all URLs share one date and it carries no per-page freshness signal. Improving this needs the generator to read real per-file/per-post modification times → round 2.

### Open Graph / Twitter metadata
Present and complete on landing pages and blog (og:type/url/title/description/image + twitter:card=summary_large_image + image alt). No action required for correctness.
**Deferred (asset, visible):** `og-default.png` is 1024×1024 (square); most social platforms crop to ~1.91:1 (1200×630). Producing a 1200×630 OG image is a design asset task → round 2.

### Existing JSON-LD
Rich coverage: Organization, WebSite, WebPage, SoftwareApplication, WebApplication, Article, FAQPage, BreadcrumbList, HowTo, Service, Offer, ImageObject. All blocks parse as valid JSON.
**Repaired this round** (malformed/broken only — see §3): a broken Organization `logo` URL, an invalid `@type: "Guide"` on two pages, and relative image/logo URLs in structured data on seven hand-authored pages.
**Deferred (needs verified data / out of round-1 scope):** no `aggregateRating`/`review`; empty `sameAs`; `SoftwareApplication` vs the more specific `MobileApplication`; inconsistent Organization legal name; `Offer` price normalization. See §5 — these require verified external data (ratings, entity name, pricing) and are explicitly outside a non-visible round.

### Heading structure
Every audited page has exactly one `<h1>`. Hierarchy is sensible.
**Deferred (visible):** many landing/blog H2s are stylistic ("The marriage ends.") rather than question-form; converting to question-style H2s with direct-answer sentences is a proven GEO/AI-citation win but is a **visible copy change** → round 2.

### Public vs private routes
All routes in this repo are **public** static pages. **No private/authenticated routes exist** (the app is a separate iOS product). Nothing to protect from indexing beyond the already-disallowed `/_partials/`, `/node_modules/`, `/.netlify/`.

### Redirects
Defined in `netlify.toml`: www→non-www and http→https canonicalization (301), a set of no-trailing-slash → trailing-slash normalizations (301), `.html` pretty-URL redirects, `/alignment*` → `/coparenting-alignment-guide/` (301), and a `/*` → `/404.html` (404) catch-all. Rules are coherent. The only defect was that the **sitemap listed `/alignment/`, a redirect source** — fixed in §3. The new `seo-check.js` now fails the build if any sitemap URL is a redirect source, preventing regressions.

### Broken internal links
The existing `automation/check-links.js` only validates that `llms.txt` URLs resolve to files and appear in the sitemap — it does **not** crawl on-page `<a href>`/`<img src>`. A manual review of nav/footer/partials targets found no broken internal links. A full internal-link crawler is a recommended round-2 test addition (documented in §5).

### Duplicate URL variants
Handled by the trailing-slash and www/http redirect rules. Canonicals are self-referential and absolute. No duplicate-content exposure found.

### Pages returning non-200
Cannot be confirmed live from the sandbox (§0). Derived expectation: all committed pages → 200; configured redirects → 301; unknown paths → 404 via the catch-all. **To be confirmed on the Deploy Preview** (see §2 status column caveat).

### Pages missing from the sitemap
**Found:** the 6 state child-support calculators (`/calculators/support/{california,florida,illinois,new-york,pennsylvania,texas}.html`) existed and were internally linked but absent from both `sitemap.xml` and `llms.txt`. **Fixed** in §3.

### Pages that may be unintentionally indexable
None found. There is no staging/private content in the repo. (Netlify Deploy Previews are automatically served with `X-Robots-Tag: noindex` by the platform — see §6 — so this branch's preview will not be indexed.)

### Pages that may be unintentionally blocked
None. No content path is disallowed in `robots.txt`; no page carries `noindex`.

### Initial-HTML rendering of important content
All primary content and metadata are present in the initial HTML for every page (static site). Verified by reading raw source. No JS-dependent content-rendering risk for crawlers.
**Deferred (a11y, visible-adjacent):** on the homepage, `.fade-in` sections start at `opacity:0` and are revealed by an IntersectionObserver — content is in the HTML (so crawlers see it) but is visually hidden if JS fails. This is an accessibility/robustness item, not a crawl-indexability item → round 2.

### Significant technical performance problems
- **Unoptimized PNG screenshots:** `app-icon.png` (~473KB), `shared.png` (~413KB), `expense.png` (~386KB), `cal.png` (~379KB), `Today.png` (~375KB). No WebP/AVIF anywhere. Converting would cut ~70–80%. Biggest perf lever. **Deferred to round 2** (asset pipeline; non-SEO-technical).
- **473KB `app-icon.png` used as a ~24px footer icon** — should use a small dedicated asset. Deferred.
- **Render-blocking Google Fonts** stylesheet (has `display=swap` + preconnect, so mitigated). Deferred.
- Only 4/136 `<img>` have width/height (CLS risk). Deferred.

None of the performance items are done this round: they either touch assets/visible rendering or fall outside "technical SEO, non-visible." All are recorded for round 2.

## 4. Blog artifacts — important note for reviewers

The committed `blog/*.html` files carry relative `/images/app-icon.png` in their Article JSON-LD, **but these are stale build artifacts.** The current `build-blog.js` generator already emits **absolute** `https://getclearly.app/images/blog-og.png`. On the next Netlify build the 101 posts regenerate with correct absolute URLs. Therefore:
- The 101 blog files were **deliberately not hand-edited** — doing so would create a 101-file diff that the next build overwrites anyway. The generator (source of truth) is already correct.
- On the Deploy Preview, the blog Article schema will show absolute URLs (freshly generated). This is expected and matches what live production already serves after its last deploy.
- `seo-check.js` intentionally scopes the "absolute URL / canonical" checks to hand-authored pages (not generated `blog/*.html`) for this reason; it still validates blog JSON-LD parses and uses valid types.
